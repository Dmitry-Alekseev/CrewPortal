# Crew Portal Developer Guide / FAQ

Документ описывает проект Crew Portal 3.0.2. Цель — дать новому разработчику карту кода, состояния и business rules, а также показать безопасные точки изменения.

## 1. Быстрый старт

Технологический стек:

- Android application, `minSdk 26`, `targetSdk 35`, `compileSdk 35`;
- Kotlin 1.9.24;
- Jetpack Compose + Material 3;
- Room 2.6.1 для roster duties;
- Preferences DataStore 1.1.1 для настроек и агрегированного flight time;
- Retrofit/OkHttp для weather и update metadata;
- Gradle wrapper 8.7, Android Gradle Plugin 8.5.2, JDK 17.

Локальная сборка:

```text
gradlew.bat testDebugUnitTest lintDebug assembleDebug --warning-mode all
```

GitHub: workflow `.github/workflows/android-build.yml` выполняет те же tests/lint/build и публикует APK и reports как artifacts. Не заменяйте wrapper на Gradle 9.x: используемые Kotlin/kapt/AGP versions проверялись для Gradle 8.7.

## 2. Общая архитектура

```text
Compose screens
    ↓ collect Flow / call suspend actions
Repositories (Flight, Preferences, Auth, Weather, Update)
    ↓
Room FlightDao + Preferences DataStore + static domain catalogs
    ↑
RosterGenerator / RosterChangeEngine / notification scheduler
```

`MainActivity` создаёт repositories вручную и передаёт их в `MainNavigation`; dependency-injection framework отсутствует. Главный persisted domain object — `FlightEntity`. Его записи одновременно представляют operating sectors, ground duties, OFF, STAY, RESERVE и DEADHEAD.

Важный принцип времени: `departureDateTime` и `arrivalDateTime` хранят локальные часы соответствующих аэропортов в формате ISO local date-time. Offset не записан в Room. Поэтому преобразование между аэропортами всегда должно проходить через IATA и `arrivalLocalDateTime`; нельзя вычислять cross-timezone arrival простым `plusMinutes`.

## 4. Основные models и persistence

### FlightEntity

Файл: `app/src/main/java/com/example/crewportal/data/local/FlightEntity.kt`.

`FlightEntity` — Room row и единая roster duty model.

| Поля | Значение |
|---|---|
| `id` | Primary key. Для generated/manual duties содержит дату, flight number и route. |
| `airline`, `flightNumber` | Display identity. Для OFF/STAY/RESERVE поле flightNumber используется как label. |
| `aircraftLabel`, `aircraftFullName`, `registration` | Тип, полное имя и назначенный борт; `TBA` означает, что registration ещё не назначена. |
| `status`, `dutyType`, `dutyNote` | Business status/type/описание. `dutyType` участвует во всех фильтрах и расчётах. |
| airport fields | IATA/ICAO/city/airport для departure и arrival. |
| `departureDateTime`, `arrivalDateTime` | ISO airport-local timestamps. |
| `durationMinutes` | Authoritative block/credited duration. Не выводите block time как разницу локальных часов. |
| `isRegistered`, `isCompleted`, `isFlightTimeAdded` | Idempotency flags регистрации, completion и credit. |
| notification flags | Не дают повторно публиковать registration/roster/airport notifications. |
| `gate`, `stand`, `terminal` | Airport position state, initial value `Pending`. |

### Room

Файлы: `AppDatabase.kt`, `FlightDao.kt`.

- database name: `crew_portal.db`;
- schema version: 3;
- table: `flights`;
- `observeAll/observeCompleted/observeById` питают Compose screens;
- write methods изменяют отдельные idempotency flags или заменяют roster snapshot.

В версии 2.2.8 schema повышена до 4 через явную `MIGRATION_3_4`; в 2.2.10 schema 5 добавлена через `MIGRATION_4_5`. Destructive fallback удалён. Перед следующим schema bump добавьте `Migration(old, new)`, SQL alterations, migration test и только затем увеличивайте `version`.

### Preferences DataStore

Файл: `PreferencesRepository.kt`, store name `crew_settings`.

Хранит login/remember state, theme/language, cumulative total/PIC/type flight minutes, installed app version, next-roster flags, 90h choice, hidden generator flag, read/deleted message IDs.

Главные state combinations:

| `prepared` | `reviewed` | Смысл |
|---|---|---|
| false | false | Следующего roster draft нет. |
| true | false | Draft доступен, требуется review. |
| true | true | Draft просмотрен; остаётся preview до смены active month. |

`setNextMonthRosterDecision(reviewed, enhancedTarget)` атомарно записывает эти flags. `resetNextMonthRosterDecision()` очищает их при удалении/новой генерации draft.

### Static/in-memory sources

`AirportDatabase`, `AircraftPool`, `CrewPool`, `MelDatabase`, `CompanyMessages` — Kotlin catalogs. `LeaveDatabase` — reactive compatibility cache; authoritative personal leave хранится в Room `leave_periods` и восстанавливается `LeaveRepository`.

## 5. Repositories и важные функции

### FlightRepository

Файл: `data/repository/FlightRepository.kt`. Это главный orchestration layer.

| Функция | Параметры | Что делает / меняет | Зависимые экраны |
|---|---|---|---|
| `observeFlights()` | — | Возвращает Room `Flow<List<FlightEntity>>`. | Roster, Calendar, Payroll, Notifications, History, Messages. |
| `observeCompleted()` | — | Completed operating flights. | Logbook. |
| `observeFlight(id)` | duty id | Один duty Flow. | Flight Details, MEL navigation. |
| `loadScheduleFromAssetsIfNeeded()` | — | Если Room пуст, генерирует current month, inserts и schedules alarms. Если есть хотя бы одна запись — ничего не меняет. | App bootstrap. |
| `refreshBuiltInRosterOnAppUpdate(versionName)` | installed build version | Безопасно seed-ит только пустую БД и обновляет version marker. Не перегенерирует опубликованный current roster и не сбрасывает permanent one-time generator flag. | MainActivity. |
| `refreshCompletedFlights(showNotifications)` | publish OS notifications или нет | Применяет due roster change, назначает registration/gate, отмечает arrivals completed и ровно один раз добавляет flight time. | MainActivity, pull-to-refresh, Settings sync. |
| `registerFlight(id)` | flight id | Назначает aircraft/airport position, propagates registration на paired turnaround и ставит `isRegistered`. | Roster/Flight Details action. |
| `generateNextMonthRosterOnce()` | — | До штатной day-27 gate генерирует `YearMonth.now()+1`, только если target rows отсутствуют. После успешной транзакции ставит permanent DataStore flag; update/delete/restart его не сбрасывают. | Пять нажатий по версии в Settings + confirmation. |
| `deleteNextMonthRosterDraft()` | — | Удаляет только next-month rows и сбрасывает review flags. Current roster сохраняется. | Settings. |
| `reconcileRosterWithApprovedLeave(showNotification)` | notification flag | Удаляет non-completed future duty, пересекающие persisted approved leave; reschedules notifications. | LeaveRosterSyncWorker, Roster, Calendar, Payroll. |
| `setNextMonthRosterDecision(reviewed, enhancedTarget)` | review и 90h flags | Persist review state; при 90h публикует informational notification. | Calendar review dialog. |
| `publishExtraDutyForSelectedTarget()` | — | Находит OFF/RESERVE date, добавляет deterministic SIN turnaround с marker `EXTRA-90H-*`. | Messages action. |
| `addOperationalRosterChange(...)` | date/time/flights/destination/aircraft/registration/pattern/return/replace/instructorRole | Удаляет только разрешённые rows, строит manual duty, inserts, reschedules alarms и уведомляет. | Hidden Operational Roster Change dialog, Roster, Calendar, History. |
| `addAircraftDeliveryPlan(request)` | date/flight/type/HS-registration | Атомарно заменяет обычные duty на затронутых датах полной delivery chain; qualification groups защищены. | Simplified Aircraft Delivery form, Roster, Calendar, Flight Details, Fleet. |
| `simulateRosterChange()` | — | Публикует demo monitoring notification; roster не переписывает. | Developer/testing actions. |

`addOperationalRosterChange` details:

- `pattern`: `TURNAROUND` или `LAYOVER`;
- `replaceExisting=false`: удаляются только `OFF`, `RESERVE`, `STAY` на affected dates;
- `replaceExisting=true`: caller явно разрешает заменить operating rows;
- `instructorRole`: `""`, `CAPTAIN_INSTRUCTOR` или `INSTRUCTOR_OBSERVER`; общий mapping находится в `data/crew/InstructorRole.kt`;
- route info идёт через `manualRoute`, airport fallback — через `AirportDatabase`, hotel — через `CrewHotelDirectory`;
- arrivals рассчитываются `arrivalLocalDateTime`.

### PreferencesRepository

Файл: `data/repository/PreferencesRepository.kt`.

`setLoginState`, `logout`, `setDarkTheme`, `setAppLanguage` меняют UI/session state. `addFlightTime(minutes, aircraftLabel)` увеличивает total, PIC и соответствующий A320/A330/A350 bucket; вызывается только после operating `FLIGHT` arrival и guarded by `isFlightTimeAdded`.

### AuthRepository

Файл: `data/repository/AuthRepository.kt`.

`validate(login, password)` выполняет локальную demo-validation. `signIn(login, rememberMe)` и `signOut()` меняют DataStore через PreferencesRepository. LoginScreen зависит от этих функций.

### WeatherRepository / WeatherApi

Файлы: `data/remote/WeatherRepository.kt`, `WeatherApi.kt`.

`getReport(icao)` делает два network calls (METAR/TAF) и возвращает `Pair<String,String>`. WeatherScreen добавляет presentation-level interpretation; runtime errors показываются через Snackbar.

### UpdateRepository

Файл: `data/update/UpdateRepository.kt`.

- `checkForUpdate()` читает `updateUrl`, парсит `AppUpdateInfo`, при network/JSON error возвращает `null`;
- `openDownload(url)` запускает external browser/installer intent;
- Settings и Update Center отображают result.

## 6. Roster generator

### RosterGenerator.generateForMonth

Файл: `data/roster/RosterGenerator.kt`.

Параметр: `YearMonth`. Результат: полный список `FlightEntity` этого месяца без database side effects.

Основной порядок:

1. Создать randomized target около 78–80 block hours.
2. Зарезервировать обязательные qualification events для зафиксированных месяцев.
3. Размещать TAS special patterns, layovers и turnarounds с occupied-day и 12h-rest checks.
4. Top-up короткими turnarounds до realistic target.
5. Добавить 1–2 reserve duties.
6. Заполнить оставшиеся даты `OFF`.
7. Для August 2026 добавить Line Check marker к ближайшему подходящему flight.

Generator не пишет в Room. Любой caller обязан решать, какой месяц разрешено заменить, затем schedule notifications.

### TAS rules

Файл: `data/roster/TashkentRotationFactory.kt` — единственный source of truth.

Thursday pattern:

- Thursday: TG684 BKK–TAS operating;
- Friday: STAY;
- Saturday: STAY;
- Sunday: TG685 TAS–BKK operating return;
- monthly operating block credit: `395 + 405 = 800` minutes.

Sunday pattern:

- Sunday: TG684 BKK–TAS operating;
- arrival local TAS Sunday 13:55 for 09:20 BKK departure;
- deadhead TG685 departs TAS Sunday 16:00 (same local calendar day);
- timezone-correct BKK arrival is Monday 00:45;
- deadhead has `dutyType=DEADHEAD` and `durationMinutes=0`, поэтому monthly flight time получает только 395 operating minutes.

Правило применяется к новым generated months. `refreshBuiltInRosterOnAppUpdate` не заменяет существующий published current month только для исправления legacy TAS timestamps/patterns.

### Timezone calculations

Файл: `util/AirportTime.kt`.

`arrivalLocalDateTime(departureLocal, departureIata, arrivalIata, blockMinutes)`:

1. Берёт offsets из `AirportDatabase`.
2. Интерпретирует departure как local time departure airport.
3. Добавляет block minutes к instant.
4. Переводит instant на arrival airport offset.
5. Возвращает arrival-local `LocalDateTime` для существующего Room format.

Для неизвестного airport используется legacy `departure.plusMinutes(blockMinutes)`, чтобы старые/custom records оставались читаемыми. Добавляя airport, обязательно заполните `utcOffsetMinutes`, иначе timezone-safe conversion невозможен.

`TimeUtils.dutyMinutes(...)` использует authoritative block duration плюс 90 minutes report и 30 minutes post-flight. Это предотвращает ошибку, когда разность BKK-local и TAS-local часов ошибочно принималась за elapsed duty time.

### RosterMetrics

Файл: `data/roster/RosterMetrics.kt`.

- `dutiesForMonth(roster, month)` фильтрует по stored departure month;
- `blockMinutes(roster, month, includedDutyTypes, completedOnly)` суммирует `durationMinutes` только выбранных duty types.

Roster Monthly Progress считает только operating `FLIGHT` с `flightTimeCreditEligible=true`, исключая dates, закрытые LeaveDatabase. Planned берёт все такие duties, completed — только `isCompleted=true`. SIMULATOR/MEDICAL/SAFETY, instructor-observer Line Check, DEADHEAD/STAY/OFF/RESERVE не входят.

Cumulative Profile flight time обновляется иначе: только завершённые `FLIGHT`, один раз на sector. Payroll block использует completed `FLIGHT`; если completed ещё нет, показывает planned `FLIGHT` как projection.

## 7. Operational Roster Change

UI: `ScheduleScreen.kt`, функция `OperationalRosterChangeDialog`.

State change: `FlightRepository.addOperationalRosterChange`.

Flow:

1. Hidden company-sync tap открывает dialog.
2. User выбирает date/report, outbound/return, airport, aircraft, optional registration, turnaround/layover, replace-existing и instructor mode.
3. Repository вычисляет affected dates.
4. Разрешённые существующие duties удаляются по ids.
5. `buildManualDuty` создаёт outbound, optional STAY rows и return.
6. Room observers мгновенно обновляют Roster/Calendar/History.
7. Alarms пересоздаются и публикуется notification.

Для добавления нового field сначала меняйте dialog callback, затем public repository function, затем `buildManualDuty`. Если field persisted в `FlightEntity`, обязательна Room migration.

## 8. Calendar state

Файл: `ui/calendar/CalendarScreen.kt`.

Calendar собирает Room duties и LeaveDatabase periods, группирует по local departure date. State `viewGeneratedMonth` локален экрану; доступность next month определяется одновременно DataStore `nextMonthRosterPrepared` и фактическим наличием rows следующего месяца.

Corporate actions:

- `Show new roster` — next draft ещё не reviewed;
- `Show next roster` — reviewed preview;
- `Show next month` — roster screen month switch;
- `I have reviewed the roster` — открывает target decision.

Все primary buttons используют `CorporateBlue`; secondary actions используют neutral/outlined styling.

## 9. Payroll

Файл: `ui/payroll/PayrollScreen.kt`, функция `calculatePayslip(month, flights)`.

Input: month и полный roster snapshot. Output: `PayslipCalc`.

Текущие formulas:

- block: completed FLIGHT, либо planned FLIGHT projection;
- flight pay: block hours × 95;
- duty pay: 90 minutes per sector + 30 minutes per unique operating date, plus paid ground minutes, × 24/hour;
- reserve: 120/day;
- deadhead: 180 per DEADHEAD row;
- night premium: local-clock night minutes × 95/hour;
- holiday premium: 1.5 multiplier for hardcoded holidays;
- augmented rest, layover and leave — отдельные additions;
- tax 12%, provident 4%, fixed insurance/welfare when gross > 0.

`unusedLeaveCompensation` содержит ограниченную placeholder-модель prior-year balance. Это известное ограничение, не persisted accounting ledger.

## 10. Messages и notifications

### Messages

`MessagesScreen.kt` строит inbox из roster/review/90h state и хранит read/deleted IDs в DataStore. `CompanyMessages.kt` — отдельный static list, который сейчас выводится на Notifications screen.

### OS notifications

| Файл | Роль |
|---|---|
| `NotificationHelper.kt` | Channel creation и immediate notification. |
| `RosterNotificationScheduler.kt` | AlarmManager events для registration/airport assignment. Airport local time конвертируется в epoch через airport offset. |
| `RosterAlarmReceiver.kt` | Получает alarm Intent и вызывает NotificationHelper. |
| `FlightRepository.refreshCompletedFlights` | State-driven registration/assignment/completion/change notifications. |

После любого roster replace/insert вызывайте `RosterNotificationScheduler.scheduleRoster`, иначе старые PendingIntents останутся несогласованными.

## 11. Airports, routes и hotels

### Airports

`AirportDatabase.kt` содержит `AirportInfo`: IATA, ICAO, name/city/country, UTC offset, elevation, runways и operational notes. `byIata/byIcao/search/all` используются autocomplete, details, weather и time calculations.

`AirportAssignmentPool.assign(departureIata, aircraftLabel, durationMinutes, seed)` deterministically выбирает gate/stand/terminal. Один flight id получает стабильный result.

### Routes

- generated turnarounds/layovers: `RosterGenerator.kt`;
- manual duration fallback: `FlightRepository.manualRoute`;
- reference-only company list: `CompanyRoutesScreen.kt`;
- route-map airport coordinates: `data/airport/AirportGeoDirectory.kt`.

Route definitions пока не сведены в единую full route table, поэтому новый route необходимо согласованно добавить во все нужные consumers. Airports и hotels уже вынесены в shared catalogs.

### Hotels

`CrewHotelDirectory.kt` — общий source of truth. Generated layovers, manual duties, TAS STAY и Flight Details читают его через `hotelFor(iata)`. Unknown IATA возвращает city-specific `Company contracted hotel — <city>`.

## 12. Fleet, Aircraft Delivery и MEL

### Fleet

`AircraftPool.kt` содержит `FleetAircraft`, включая исторический парк A380 для сценария 2026. `assignFor(aircraftLabel, routeClass, flightId)` нормализует type, не пересекает aircraft families и deterministically выбирает registration. `byRegistration` используется MEL/details.

Правила A380 разделены между несколькими source of truth:

- `A380QualificationPolicy.kt` — дата появления rating, роль First Officer до конца 2026 и возврат к Captain с 01.01.2027;
- `A380TransitionProgram.kt` — одноразовый October/November 2026 training/positioning сценарий;
- `RouteCatalog.a380Eligible` — совместимость аэропорта плюс предел 8000 NM;
- `PreferencesRepository` — отдельный `a380_minutes`; A380 FO увеличивает total/type time, но не PIC;
- `FlightDetailsScreen`/`CrewPool` — First Officer crew placement и скрытие e-logbook до 2027.

### Aircraft Delivery — Crew Portal 3.0

`data/delivery/AircraftDeliveryPlanner.kt` — единый источник delivery routing. `AircraftDeliveryRequest` принимает дату, номер рейса, type и registration. `build()` детерминированно создаёт BKK-DXB-HAM passenger positioning, затем XFW/EDHI → GYD/DWC/DOH/MCT → BKK. EDDH-EDHI row намеренно отсутствует. Для двух пилотов planner создаёт `CREW_REST` 8-12h; для четырёх — `TECHNICAL_STOP` 2-4h и противоположные operating/passenger roles по лэгам.

`FlightRepository.addAircraftDeliveryPlan` выполняет одну atomic roster replacement. `refreshCompletedFlights` вызывает `FleetRepository.addDeliveredAircraft` только для финального delivery row с `arrivalIata == BKK`, поэтому промежуточное прибытие не активирует борт. `deliveryProcessed` и Room upsert сохраняют idempotency.

### MEL

`MelDatabase.kt` генерирует deterministic defects по registration, aircraft family и month. Главные методы: `forAircraft(registration, month)`, `all()`, `fromJson(json)`. MelScreen и FlightDetails technical card зависят от registration. Добавляя aircraft type, обновите family filters в MEL templates.

## 13. Profile, leave и logbook

- `ProfileScreen.kt` отображает DataStore total/type minutes и static qualifications/profile details.
- `LeaveDatabase.kt` объединяет company-assigned, date-bounded planned personal, persisted approved personal и closed sick periods; `adjustedMonthlyTargetMinutes` уменьшает 80h target пропорционально уникальным leave periods. October 2026 company leave заканчивается 8-го, personal extension занимает 9-14-е.
- `LeaveManagementScreen.kt` сохраняет approved request через `LeaveRepository`; `LeaveRosterSyncWorker` примерно через пять минут физически удаляет конфликтующие future roster rows.
- `LogbookScreen.kt` читает completed flights из Room.

`LeaveRosterSyncScheduler` использует unique one-time WorkManager с initial delay 5 минут, поэтому закрытие экрана или process death не теряет применение отпуска.

## 14. Version/update system

Version source для Android: `app/build.gradle.kts`, `versionCode` и `versionName`.

Remote check source: `update/app_update.json`, который должен быть опубликован по URL из `UpdateRepository.updateUrl`.

Release workflow: `.github/workflows/release-apk.yml`; input version определяет tag и artifact file name. Workflow собирает debug-signed APK существующим debug keystore — это не production Play signing.

При version bump синхронно обновите:

1. `app/build.gradle.kts`;
2. `update/app_update.json` и APK URL;
3. `README.md`;
4. `CHANGELOG.md`;
5. hardcoded artifact name в `.github/workflows/android-build.yml`;
6. release input/tag при запуске workflow.

## 15. How to change...

### ...добавить новый аэропорт

1. Добавьте `AirportInfo` в `AirportDatabase.airportList`, особенно правильный `utcOffsetMinutes`.
2. Добавьте offline coordinate в `AirportGeoDirectory`; карта и fallback block-time используют один источник.
3. Если airport имеет специальные gates/stands, расширьте `AirportAssignmentPool`.
4. Добавьте timezone test для route с новым airport.

### ...добавить маршрут

1. Generated route: добавьте `TurnaroundRoute` или `LayoverRoute` в `RosterGenerator`.
2. Manual ORC: добавьте min durations в `FlightRepository.manualRoute`; airport metadata подтянется из AirportDatabase.
3. Reference screen: добавьте `CompanyRoute` в `CompanyRoutesScreen`.
4. Добавьте airport/map/hotel при необходимости.
5. Проверьте target block, rest, span days и aircraft compatibility tests.

### ...изменить min/max block time

- Sector block: `outboundMinutes/inboundMinutes` в route definitions и `manualRoute`.
- Monthly generator target: `targetBlock` в `RosterGenerator.generateForMonth`.
- Top-up ceiling: condition рядом с `82 * 60 - plannedBlock`.
- Monthly displayed target: `MonthlyProgressCard` и `LeaveDatabase.adjustedMonthlyTargetMinutes`.
- 90h choice: `setNextMonthRosterDecision` и `publishExtraDutyForSelectedTarget`.

Изменяйте `durationMinutes`, а не вычисляйте block по local timestamps.

### ...добавить registration

Добавьте `FleetAircraft` в `AircraftPool.aircraft` с правильными `label` и `routeClass`. Если label новый, расширьте `normalizeLabel`, generator choices, MEL family matching и UI filters. `assignFor` должен сохранять запрет cross-family fallback.

### ...изменить crew hotel

## 16. Tests и CI

Unit tests:

- `AirportTimeTest` — BKK/TAS offsets и unknown-airport fallback;
- `TashkentRotationFactoryTest` — Friday/Saturday STAY, Sunday operating return, same-Sunday deadhead departure и block credit;
- `RosterMetricsTest` — monthly duty-type/completion filters.

GitHub workflow выполняет:

```text
./gradlew testDebugUnitTest lintDebug assembleDebug --warning-mode all
```

Reports и APK публикуются отдельными artifacts. Release workflow сначала выполняет те же проверки и только затем создаёт GitHub Release.

## 17. Известные ограничения

- Aircraft Delivery и fleet persistence реализованы; production approval/audit остаются внешними требованиями.
- Leave records persisted в Room; compatibility cache остаётся для legacy synchronous consumers.
- Общие route facts находятся в `RouteCatalog`; generator-specific flight numbers/times остаются в `RosterGenerator`.
- Next-month due-date function запускается immediate/daily WorkManager worker.
- Payroll — local projection, не authoritative payroll backend.
- Room 3→4 использует явную migration без destructive fallback; future schema changes требуют новых migrations.
- GitHub Release публикует installable debug APK и не требует signing secrets; это testing distribution, не Play Store signing.
- Local Android compile зависит от установленного Android SDK; GitHub CI является подготовленной воспроизводимой build path для этого архива.

## 18. Safe change checklist

1. Найдите source of truth и все consumers через `rg`.
2. Не меняйте current published roster при update/generator-rule change.
3. Для persisted field подготовьте migration до schema/version bump.
4. Для времени всегда определите, local clock какого airport хранится.
5. Для roster mutation сохраняйте stable ids/flags и reschedule alarms.
6. Добавьте unit test business rule.
7. Запустите GitHub Android CI; исправьте tests, compile, lint warnings.
8. Обновите guide/changelog/version metadata, если public behavior/version изменились.

## 19. Изменения архитектуры в 2.2.8

Этот раздел заменяет устаревшие ограничения из раздела 17 для версии 2.2.8.

### Room и migration 3 → 4

`data/local/AppDatabase.kt` теперь содержит четыре сущности: `FlightEntity`, `LogbookEntryEntity`, `FleetAircraftEntity`, `LeavePeriodEntity`. `DatabaseMigrations.kt` добавляет новые таблицы и поля к существующей таблице `flights`; current roster не удаляется. `fallbackToDestructiveMigration()` удалён.

Новые поля `departureEpochMillis` и `arrivalEpochMillis` хранят UTC instant параллельно с legacy airport-local ISO strings. `FlightRepository.backfillUtcInstants` заполняет их через `airportLocalEpochMillis`. Local strings сохранены для совместимости UI и прежнего persistence format.

`FlightDao.replaceAll` помечен `@Transaction`. Его используют automatic roster change, повторная генерация draft, удаление draft и manual Operational Roster Change. Между `DELETE` и `INSERT` наблюдатели больше не увидят пустой roster.

### Electronic Logbook

- entity/DAO: `data/local/LogbookEntryEntity.kt`, `LogbookEntryDao.kt`;
- repository: `data/repository/LogbookRepository.kt`;
- UI: `ui/schedule/ElectronicLogbookCard.kt`, подключён из `FlightDetailsScreen.kt`.

Поля соответствуют EASA FCL.050/AMC1: дата, flight number, departure/arrival place and time, make/model/variant, registration, PIC name, pilot function, total/PIC/SIC/night/IFR/instrument time, take-offs, landings, approaches, remarks и electronic signature. `saveDraft` обновляет незаверенную запись. `certify` требует signature, registration и положительный total time, ставит `certifiedAtEpochMillis`; UI после этого блокирует случайное редактирование.

Нормативные источники формы: [EASA Easy Access Rules for Aircrew — FCL.050/AMC1](https://www.easa.europa.eu/en/document-library/easy-access-rules/online-publications/easy-access-rules-aircrew?erules-id=ERULES-1963177438-10451) и [FAA AC 120-78B — Electronic Signatures, Electronic Recordkeeping, and Electronic Manuals](https://www.faa.gov/regulations_policies/advisory_circulars/index.cfm/go/document.information/documentID/1043396).

Чтобы изменить набор полей, одновременно обновите entity, SQL migration следующей версии, repository prefill/validation, Compose form и CSV/export consumer. Для юридически значимого production logbook дополнительно нужны серверная identity, audit trail, amendment history, backup/retention и политика авиационных властей.

### Aircraft Delivery / Ferry

- type metadata: `data/fleet/AircraftTypeCatalog.kt`;
- route/crew/rest rules: `data/delivery/AircraftDeliveryPlanner.kt`;
- persisted aircraft: `FleetAircraftEntity`, `FleetAircraftDao`, `FleetRepository`;
- input: simplified delivery branch in `OperationalRosterChangeDialog`;
- duty creation/completion: `AircraftDeliveryPlanner.build`, `FlightRepository.addAircraftDeliveryPlan`, `refreshCompletedFlights`;
- display: `FleetScreen` observes Room.

Delivery form показывает только дату, flight number, один из пяти разрешённых типов и suffix после неизменяемого `HS-`. Planner добавляет passenger positioning и два ferry legs. A330-800neo и A330-900neo имеют разные specs и не нормализуются в A330-300. После финального BKK arrival `FleetRepository.addDeliveredAircraft` выполняет upsert, затем `deliveryProcessed` делает переход idempotent. До прибытия новый борт в assignment pool не попадает.

Как добавить новый deliverable aircraft type: добавьте `AircraftTypeSpec` в `AircraftTypeCatalog.types`. UI получает список автоматически. Если требуется особая совместимость маршрутов, обновите `FleetRepository.normalizeLabel/assignFor` и добавьте unit test.

### Leave, payroll, routes и duty types

Approved personal leave сохраняется через `LeaveRepository`/`LeavePeriodDao`; при старте cache `LeaveDatabase` восстанавливается для совместимости synchronous consumers. Для изменения approval delay правьте только `APPROVAL_DELAY_MINUTES` в `LeaveRosterSyncWorker.kt`.

Payroll policy вынесена из Compose в pure `data/payroll/PayrollCalculator.kt`. Меняйте rates и формулы там; `PayrollScreen` только выбирает месяц и отображает `PayslipCalc`.

`data/route/RouteCatalog.kt` — общий справочник airport metadata, block times, aircraft class, operation type и hotel для Company Routes и manual roster changes. Generator-specific flight numbers/times остаются в `RosterGenerator`, но общие route facts не следует дублировать.

`data/local/DutyType.kt` определяет стабильные persisted values. Новые проверки должны использовать `DutyType.*.value`; изменение уже сохранённого value требует Room data migration.

### Generator и публикация следующего месяца

`RosterGenerator.generateForMonth(month, seed)` детерминирован. Default seed зависит только от месяца и `GENERATOR_RULESET_VERSION`. Для изменения правил увеличьте ruleset version и обновите tests; уже опубликованный current month всё равно не регенерируется при app update.

`NextRosterScheduler` регистрирует immediate и daily WorkManager jobs. `NextRosterWorker` восстанавливает persisted leave в `LeaveDatabase`, затем вызывает публичный idempotent `prepareNextMonthRosterIfDue`; дата генерации — 27-е число текущего месяца. Менять дату нужно только в этой функции и соответствующем тесте.

### Release signing

GitHub signing secrets и `KEYSTORE_BASE64` не нужны. В проект возвращён legacy `app/crewportal-debug.keystore`, полностью совпадающий с ключом предыдущего архива; `app/build.gradle.kts` использует его для debug build. Это сохраняет signing certificate и локальную Room/DataStore БД при обновлении поверх установленной 2.2.x. `android-build.yml` и `release-apk.yml` собирают `testDebugUnitTest`, `lintDebug`, `assembleDebug`; release workflow прикладывает APK к GitHub Release. Для Google Play позднее потребуется отдельная production-signing схема.

## 20. Public map и route-duration policy в 2.2.10

`data/airport/AirportGeoDirectory.kt` — единый встроенный каталог координат. `FlightDetailsScreen.PublicRouteMap` создаёт native `MapView`, загружает публичный OpenFreeMap Liberty style через MapLibre и поверх него рисует маршрут и точки вылета/прилёта. API key, WebView и Google Maps SDK не используются. Для карты нужен доступ к `tiles.openfreemap.org`; при отсутствии сети остальные flight details продолжают работать.

`RouteCatalog.byIata` сначала возвращает явное company value. Для LED это 650/625 минут, для LHR — 760/705 минут. Если airport известен, но явной route entry нет, `estimatedRoute` вычисляет conservative scheduled block из great-circle distance `AirportGeoDirectory.distanceNm`; fixed fallback 150/150 удалён. Company Routes показывает форматированное время отдельно для outbound и inbound.

STAY title не доверяет legacy `departureCity`: Calendar, Roster и Flight Details вызывают `AirportDatabase.cityName(iata, fallback)`. Сам hotel остаётся в `departureAirport`/`arrivalAirport` и `dutyNote`, поэтому location heading и accommodation больше не смешиваются.

Чтобы добавить маршрут с картой:

1. добавьте airport metadata в `AirportDatabase`;
2. добавьте coordinate в `AirportGeoDirectory`;
3. для company route добавьте explicit block times в `RouteCatalog`;
4. для generated rotation добавьте flight-number/time template в `RosterGenerator`;
5. при layover добавьте hotel в `CrewHotelDirectory`;
6. добавьте unit test exact block time и наличие coordinate.

## 21. Qualifications, linked events и Room schema 5

`data/qualification/PilotQualificationSchedule.kt` — source of truth для Medical, Simulator, Line Check и SEP. `QualificationValidity` хранит название, дату прохождения, следующую дату и периодичность. `eventsForMonth(month)` разворачивает recurring records в `ScheduledQualificationDay`: дату, duty type, title/note, общий `eventGroupId`, номер дня и размер группы, а для Line Check — operating role. Profile и Documents & Qualifications читают те же `QualificationValidity`, поэтому экранные сроки не расходятся с генератором.

`RosterGenerator.generateForMonth` сначала резервирует Leave, затем qualification groups, потом Line Check на реальном HKG turnaround и только после этого обычные рейсы/reserve/OFF. Simulator создаётся связанной группой из трёх последовательных дней, Medical — из двух. Для группы ищется целиком свободное окно; отдельный средний день не переносится. На границе месяца каждая часть получает одинаковый `eventGroupId` и правильный `eventDayIndex/eventTotalDays`. Ground events имеют нулевой block credit. Пользователь в текущем сценарии выполняет Line Check как instructor/observer, поэтому оба operating legs видны в roster, но имеют `flightTimeCreditEligible=false`.

`FlightEntity` schema 5 добавляет `rosterSource`, `eventGroupId`, `eventDayIndex`, `eventTotalDays`, `lineCheckRole`, `flightTimeCreditEligible`. `MIGRATION_4_5` добавляет columns с совместимыми defaults, помечает старые Aircraft Delivery и manual operational changes и не удаляет существующие roster rows. `FlightRepository.addOperationalRosterChange` отказывается частично заменять связанную qualification group; extra 90h duty выбирает только безопасный OFF/RESERVE день без Leave и с 12-hour rest.

`RosterMetrics`, `ScheduleScreen` и `PayrollCalculator` используют `flightTimeCreditEligible`: operating monthly flight time и block pay не включают Simulator/Medical/SEP и instructor-observer Line Check. `CalendarScreen`, `ScheduleScreen.TodayDutyCard` и `FlightDetailsScreen` показывают training title, location, group day и instructor role из persisted entity.

### How to change qualification rules

1. Измените completion/next-due и cadence в `PilotQualificationSchedule`.
2. Измените recurring template в `eventsForMonth`; для нового multi-day event задайте полный `totalDays` и стабильный `eventGroupId`.
3. Если появляется новый persisted duty type, добавьте его в `DutyType`, календарные цвета, Today’s Duty и payroll ground policy.
4. Если duty даёт operating block credit, выставляйте `flightTimeCreditEligible=true` только для фактической operating роли.
5. Не меняйте уже опубликованный current-month roster только из-за нового ruleset: `refreshBuiltInRosterOnAppUpdate` намеренно seed-ит только пустую БД.

### How to change the map provider

Style URI находится в `FlightDetailsScreen.OPEN_FREE_MAP_STYLE_URI`, Android SDK dependency — в `app/build.gradle.kts`. Новый provider должен поддерживать MapLibre style JSON и HTTPS. Координаты аэропортов остаются в `AirportGeoDirectory`; добавление аэропорта без coordinate оставит flight details доступными, но не сможет построить route overlay.
